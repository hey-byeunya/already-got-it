# 문제 정의서 — "이미 있어" 등록 자동화 + 장바구니 잔소리 봇 (PoC)

## 도메인 설명

"이미 있어"는 로그인한 사용자가 자신의 물품("있템")과 위시리스트("위시")를 관리하는 개인용 재고 관리 웹앱이다. 화장품을 시작점으로 설계됐지만 식료품·생활용품 등으로 확장 가능한 범용 구조를 목표로 한다. 앱의 핵심 가치는 두 가지다:
1. "이미 가진 걸 까먹고 또 사지 않게" — 충동구매 방지
2. 사용기한이 있는 물건(특히 화장품)을 방치해서 유통기한을 넘기지 않게 D-day로 챙겨주는 것

신규 물건을 등록할 때 사용자는 이름 · 카테고리(자유 입력, 칩 선택 보조) · 수량 · 구매일 · 사용기한(선택) · 메모(선택) · 상태를 직접 입력한다. 지금은 이 중 어떤 필드도 자동으로 채워지지 않는다 — 전부 수동 타이핑이다.

## 현재의 문제

**① 등록이 번거롭다**
- 새 물건을 등록할 때마다 이름 · 카테고리 · 사용기한을 사람이 직접 보고 옮겨 적어야 한다.
- 특히 **사용기한**은 화장품/식품 용기 옆면이나 바닥에 작은 글씨로 인쇄돼 있어서, 사람이 읽고 그대로 타이핑하는 과정에서 오타·오독이 나기 쉽다(예: `2026.08`을 `2028.06`으로 잘못 읽거나 잘못 입력). 이 앱의 존재 이유가 "사용기한을 놓치지 않는 것"인데, 그 입력값 자체가 사람 손으로 들어가는 한 정확도를 보장할 수 없다.
- 등록 자체가 번거로워서("사진 찍고 앱 열고 다 타이핑하기") 나중에 등록하려고 미루다가 결국 반영이 안 되는 물건이 생긴다.

**② "이미 있어?" 확인이 쇼핑하는 순간에 끊긴다**
- 지금은 사용자가 무언가를 사려고 할 때 스스로 "이미 있어" 앱을 열어서 검색해봐야만 중복 구매를 막을 수 있다. 정작 충동구매가 일어나는 순간(장바구니에 담을 때)에는 앱을 열어 확인하는 행동이 끼어들지 않는 한 아무 방어도 없다 — 앱의 핵심 가치 ①(충동구매 방지)이 "사용자가 능동적으로 확인해야만" 작동하는 수동적 안전장치에 그친다.
- 반대로, 장바구니에 담은 물건이 이미 있는 물건이 **아니라면** 그건 그대로 등록 대상인데, 이것도 결국 사람이 나중에 다시 손으로 등록해야 한다 — ①의 번거로움과 같은 문제가 반복된다.

이 문제는 이미 인지돼 있었다: `PRD.md`의 "Won't(오늘은 일부러 뺄 것)" 목록에 "바코드 스캔·사진 인식 자동 등록"과 "카테고리 자동 분류/AI 추천"이 명시적으로 들어가 있다 — MVP 범위에서 의도적으로 제외했던 항목이다.

## 개선 가설

두 가지 입력 경로에서 같은 OCR 컴포넌트를 재사용해 "등록 자동화"와 "충동구매 방지"를 한 파이프라인 세트로 묶는다.

### A. 사진 한 장 → 있템 등록 자동 채움

```
물건 사진 입력
  ↓
① YOLO(객체 탐지) — 사진 속 병/통 등 제품 영역의 위치를 찾아 그 영역만 크롭
  ↓
② OCR(텍스트 인식) — 크롭된 영역에서 라벨에 인쇄된 텍스트를 추출
  ↓
③ 파싱/매핑(경량 로직) — 날짜 패턴은 사용기한 후보, 나머지 텍스트는 이름 후보로 뽑고
   기존 카테고리 목록(list_owned_categories)과 키워드 유사도로 카테고리 추천
  ↓
있템 등록 폼 자동 채움 (이름 / 카테고리 / 사용기한) — 사용자는 확인·수정만 함
```

### B. 장바구니 스크린샷 → 매칭 후 분기(잔소리 봇 / 선택적 등록)

```
장바구니 화면 스크린샷 입력
  ↓
① OCR(텍스트 인식) — 화면 속 상품명 텍스트(들) 추출 — A와 동일한 OCR 컴포넌트 재사용
  ↓
② 매칭 — 추출된 각 상품명을 "있템" DB와 유사도 매칭
  │
  ├─ 매칭됨(이미 있는 물건) ─────────────────────────────────┐
  │   ③a LLM 문구 생성 — 설정된 잔소리 봇 별칭·타입·강도에 맞는 잔소리 문구 생성      │
  │   ④a TTS(음성 합성) — 생성된 문구를 설정된 보이스로 음성 경고 재생              │
  │                                                          │
  └─ 매칭 안 됨(처음 사는 물건) ──────────────────────────────┘
      ③b "있템으로 등록" / "위시로 등록" 선택 버튼 제공 (자동 등록 아님, 사용자가 선택)
          선택 시 A의 자동 채움 로직을 재사용해 OCR로 이미 뽑은 이름을 등록 폼에 프리필
```

B는 자동으로 아무것도 등록하지 않는다 — "이미 있으니 다시 생각해보라"는 경고(음성)와 "없으니 등록하겠냐"는 제안(선택 버튼)만 준다. 최종 결정은 항상 사용자가 한다.

**사용기한 미인식 시 안내 문구 (UX 보완, 코드 아님)**

1차 실험에서 사용기한 추출이 6장 중 0장 성공했는데, 원인 중 하나가 "유통기한이 사진에 찍힌 면이 아니라 다른 면(뚜껑, 바닥)에 있어서 애초에 프레임 밖"인 경우였다. 모델을 개선하는 대신, OCR 결과에 날짜 패턴이 전혀 없을 때 사용자에게 보여줄 안내 문구를 미리 정해둔다(실제 등록 UI가 생기면 그대로 적용):
- "사진에서 유통기한을 못 찾았어요. 뚜껑 안쪽이나 포장 바닥도 함께 찍어주시겠어요?"
- "이 사진만으로는 사용기한이 안 보여요 — 유통기한이 적힌 면을 한 번 더 찍어주세요."
- (짧은 버전) "유통기한 사진이 더 필요해요 (뚜껑/바닥 확인)"

세 문구 다 "실패했다"고만 말하지 않고 "어디를 다시 찍어야 하는지" 구체적으로 알려주는 것을 원칙으로 했다 — 반사광/각인처럼 사진을 다시 찍어도 안 풀리는 경우는 이 안내로 해결 안 되지만, "다른 면에 있어서 프레임 밖"인 경우는 이 안내만으로도 상당수 해결될 것으로 기대한다.

이렇게 하면 (1) 등록에 걸리는 시간과 사용기한 오타/오독 확률이 줄고, (2) 충동구매가 실제로 일어나는 "장바구니에 담는 순간"에 방어선이 하나 더 생길 것이라는 게 개선 가설이다.

## 대상 사용자

"이미 있어"를 실제로 쓰는 사용자 본인(1인 사용 케이스) — 특히 화장품처럼 유통기한 표기가 작고 등록이 잦은 품목을 다루면서, 온라인 쇼핑몰 장바구니에 물건을 담아두고 고민하는 습관이 있는 사용자가 가장 큰 도움을 받는다.

## 성공 기준 — 1차 실험 결과 반영 (2026-08-12, 샘플 6~8건 기준)

> 아래는 원래 세운 기준에, 실제 샘플(물건 사진 6장 + 장바구니 스크린샷 2장)로 돌려본 1차 실험 결과(`EXPERIMENT_RESULTS.md`)를 채워 넣은 것이다. 표본이 매우 작아(n=6~8) 통계적으로 신뢰할 수치는 아니고, "다음 라운드에 뭘 개선해야 하는지"를 짚어내는 용도로 본다.

**정량**
- (A) 이름 추출 — 6장 중 뚜렷한 브랜드/제품명이 깔끔히 뽑힌 건 2장(정면 라벨이 정상적으로 프레임에 들어온 경우), 부분적으로만 뽑힌 건 2장, 실패 2장(각인·회전 텍스트). **약 33% 완전 성공**.
- (A) 사용기한 날짜 추출 — **6장 중 0장 성공**. 가장 뼈아픈 결과: 유통기한이 뚜껑/바닥의 반사광 있는 각인 텍스트이거나(2건), 라벨 다른 면(별도 표기)에 있어 애초에 프레임 밖이거나(1건), 회전돼 있거나(1건) 해서 숫자 자체를 못 읽었다. 앱의 핵심 가치가 걸린 지표인데 지금 파이프라인으로는 사실상 자동화가 안 됨 — 다음 라운드의 최우선 개선 과제.
- (A) 카테고리 추천 — **미구현/미검증**. PoC 스크립트(`03_match_and_nag.py`)는 "있템 이름"과의 매칭만 구현했고, 카테고리 추천 로직은 아직 만들지 않았다. 원래 계획에서 빠진 부분이라 다음 라운드로 이월.
- (A) 등록 소요시간 비교 — **미측정**. 이번 실험은 "모델이 실제로 도는지"만 확인했고 수동 입력 시간과의 정량 비교는 아직 안 함. 다음 라운드(실제 등록 폼 통합 시점)에서 스톱워치로 측정 예정.
- (B) 매칭 정확도 — 테스트한 4건 중: 같은 언어(한글)로 텍스트가 있을 때는 3/3(장바구니 항목 매칭 성공 1건 + 정확한 미매칭 판정 2건) 모두 올바르게 분류됨. 다만 **언어가 다르면(영문 라벨 vs 한글 있템 이름) 1/1 실패** — 같은 제품(유세린/Eucerin)인데 유사도 0으로 완전히 못 알아봄. n이 너무 작아 비율로 일반화하긴 이르지만, difflib 문자열 유사도만으로는 다국어 라벨을 커버할 수 없다는 것은 확실히 확인됨.
- (B) 미등록 항목의 등록 소요시간 — **미측정** (A의 등록 소요시간과 같은 이유로 다음 라운드로 이월).

**정성**
- (A) 실패 사례 — 반사광/각인 텍스트(2건), 회전된 텍스트(1건), 유통기한이 다른 면에 있어 프레임 밖(1건) 세 가지 유형으로 뚜렷이 갈림. YOLO 미탐지(6장 중 3장)·오탐(1장)도 있었지만, 원본 이미지로 폴백하는 로직 덕분에 OCR 단계 자체는 끊기지 않고 계속 진행됨 — 이 폴백 설계가 유효했다는 것도 이번 실험의 성과.
- (B) 잔소리 문구 샘플 비교 — Ollama(qwen2.5:3b)로 같은 매칭 결과에 대해 다정/직설/매운맛 3종 생성 시 톤 차이가 뚜렷이 느껴졌음(다정=부드러운 되묻는 어투, 직설=명령형, 매운맛=감탄사+명령형). 다만 4회 중 1회 문구에 한자·영문 잡음이 섞이는 간헐적 생성 실패가 있었음(재현 안 됨) — 재시도/필터 로직이 필요.
- (B) 오매칭 사례 — 이번 표본에서는 "다른 물건을 같은 것으로 착각"하는 거짓양성 사례는 발견되지 않았고, 반대로 "같은 물건을 언어가 달라 못 알아보는" 거짓음성 사례가 1건 확인됨(위 매칭 정확도 참고). 거짓양성 케이스는 표본을 늘려서 추가로 확인해야 함.
- (부가) TTS 보이스 품질 — 캐릭터 보이스(Eddy/Grandma 등)는 발화가 매끄럽지 않다는 피드백을 받아 표준 보이스(Yuna) 하나로 통일하고 속도/피치만 프리셋별로 조정하는 방식으로 전환함. 원래 계획했던 "보이스 1~2종 비교"보다 "표준 보이스 하나 + 톤 파라미터 변주"가 더 안정적인 접근으로 판명됨.

## 잔소리 봇 설정 (PoC 범위)

과제 요구사항인 "잔소리 봇 별칭 · 잔소리 타입 · 음성 · 강도" 설정을 PoC에서는 설정 UI 없이 **미리 정의한 프리셋 조합**으로 검증한다(정식 기능이 되면 설정 화면을 따로 만들 수 있음):
- 별칭: 예) "잔소리 언니" / "다정한 집사"
- 타입 × 강도 프리셋 3종 예시: (1) 다정 · 약("이거 이미 있으시던데요, 그래도 괜찮아요~"), (2) 직설 · 중("이미 있는 거예요. 진짜 필요해요?"), (3) 매운맛 · 강("또요?! 저번 것도 아직 다 안 썼잖아요!!")
- 음성: (실험 결과 반영) 캐릭터 보이스별로 나누는 대신 표준 보이스(Yuna) 하나로 통일하고, 프리셋마다 속도(rate)와 피치(pbas)만 다르게 줘서 톤을 구분 — 다정(기본), 직설(170wpm·피치-10), 매운맛(235wpm·피치+15). 자세한 시행착오는 `EXPERIMENT_RESULTS.md` ④ 참고

## 모델 선정 근거 (요약)

- **YOLO**: 일반 객체 탐지만으로는 "이게 병이다"까지는 알 수 있어도 "어떤 브랜드/제품인지"는 알아낼 수 없다(COCO 클래스가 병·컵 등 범용 80종). 그래서 실제 제품 식별은 OCR이 맡고, YOLO는 사진 속에서 크롭할 영역을 잡아 OCR 입력 품질을 높여주는 보조 역할로만 파이프라인에 넣는다.
- **OCR**: A(물건 사진)와 B(장바구니 스크린샷) 양쪽에서 공통으로 쓰는 핵심 컴포넌트 — "실제로 무슨 텍스트가 적혀 있는가"를 읽어내는 역할.
- **LLM(텍스트 생성)**: 매칭 결과(이미 있음/없음)는 규칙 기반으로 판단할 수 있지만, "잔소리 문구"처럼 같은 판단에도 페르소나별로 표현이 달라지는 부분은 규칙보다 생성 모델이 적합해서 이 단계에만 넣는다.
- **TTS(음성 합성)**: "음성 경고"라는 요구사항 자체가 텍스트를 소리로 바꾸는 단계가 필요해서 넣는다. 이 프로젝트에서 별도로 다루지 않은 유일한 새 모달리티(텍스트→음성)라, 파이프라인 다양성 측면에서도 의미가 있다.

## 한계 · 다음 스텝 (1차 실험으로 확정/추가된 항목 포함)

**사전에 예상했던 것 (실험으로 확인됨)**
- 통·박스·튜브 형태 제품은 YOLO 크롭 단계 정확도가 떨어진다 — 실제로 6장 중 3장 미탐지, 1장 오탐(튜브를 cup으로). 원본 폴백 로직이 있어 파이프라인은 안 끊김.
- 비슷한 이름의 리필/용량 변형 제품 오매칭 가능성 — 이번 표본에선 발견 안 됐지만 표본이 작아 확인 안 된 것일 뿐, 여전히 열린 리스크.

**실험을 돌려보고 새로 발견한 것**
- **사용기한 추출이 6장 중 0장 성공** — 반사광 각인 텍스트, 회전된 텍스트, 라벨 다른 면(프레임 밖)이라는 3가지 실패 유형이 명확히 갈림. 이 지표가 앱의 핵심 가치와 가장 직결되는데 지금 가장 약하다. → ✅ **부분 대응 완료**: "다른 면에 있어서 프레임 밖"인 경우에 한해 안내 문구 초안 작성(위 "사용기한 미인식 시 안내 문구" 참고). 반사광/각인/텍스트 영역이 너무 작은 경우는 여전히 미해결 — 모델·전처리 개선이 더 필요함.
- **언어/문자 체계가 다르면 매칭이 아예 안 됨** — 영문 라벨(Eucerin) vs 한글 있템 이름(유세린)처럼 같은 제품인데 유사도 0. → ⚠️ **부분 개선**: `03_match_and_nag.py`에 difflib→Ollama 의미 매칭 하이브리드(`llm_semantic_match`)를 추가해 텍스트가 깨끗할 때는 정확히 매칭됨을 확인했지만, 재검증 중 OCR 잡음이 더 섞인 같은 물건 텍스트로는 LLM도 3회 모두 매칭 실패하는 걸 발견함(`EXPERIMENT_RESULTS.md` ③ 참고) — "해결"이 아니라 "노이즈에 민감한 개선"으로 정정. 신규 물건에 대한 거짓양성은 없음을 확인.
- **회전된 텍스트에 OCR이 특히 취약함** — 사전에 예상 못 했던 실패 유형. → ⚠️ **시도했으나 효과 제한적**: EasyOCR `rotation_info` 옵션을 추가했지만 해당 샘플은 여전히 실패. 재분석 결과 진짜 원인은 회전이 아니라 텍스트 영역이 프레임 대비 너무 작아서일 가능성이 높음(이미지 업스케일링/다단계 크롭 등 다른 접근이 필요, 다음 라운드로 이월).
- 카테고리 추천 로직은 이번 PoC 스크립트에 아직 구현 안 함. → ✅ **구현 완료**: `experiments/05_recommend_category.py` 신설, 실제 샘플 4건 중 3건 정확·1건 애매(카테고리 체계 자체의 경계 문제, `EXPERIMENT_RESULTS.md` ⑤ 참고).
- 등록 소요시간(수동 vs 자동) 정량 비교는 아직 측정 안 함 — 실제 등록 폼에 통합한 뒤 스톱워치로 측정 예정(**후순위 유지, 미착수**).
- 장바구니 스크린샷은 쇼핑몰마다 레이아웃이 달라서, 상품명 텍스트 영역을 구분해내는 것 자체가 OCR 이후의 파싱 난이도를 높일 수 있다 — PoC에서는 특정 쇼핑몰 1~2곳의 캡처만으로 검증 범위를 한정한다(**후순위 유지, 스코프 그대로**).
- LLM(잔소리 문구) 출력이 간헐적으로(4회 중 1회) 잡음 섞인 텍스트를 생성함. → ✅ **해결**: 한글/영문/숫자/기본 문장부호만 허용하는 검증 필터 + 3회 재시도 + 프리셋별 고정 폴백 문구 추가, 유닛 확인 완료.
