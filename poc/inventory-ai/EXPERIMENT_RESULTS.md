# AI 모델 실험 결과 (YOLO / OCR / LLM / TTS)

실제 샘플(물건 사진 6장 + 장바구니 스크린샷 2장)로 4개 모델을 로컬에서 실행한 결과. `PROBLEM.md`의 성공 기준을 채우기 위한 근거 데이터.

## 환경
- Python 3.12 venv(`uv`로 생성), Apple Silicon(arm64), CPU 실행(GPU 불필요할 정도로 가벼움)
- YOLO: `ultralytics` YOLOv8n(사전학습, 추가 학습 없음)
- OCR: `easyocr` `Reader(['ko','en'])`
- LLM: Ollama `qwen2.5:3b` (로컬, 무료)
- TTS: macOS `say` 커맨드(추가 설치 없음, 무료)

## ① YOLO 크롭 — 물건 사진 6장

| 샘플 | 탐지 결과 | 신뢰도 |
|---|---|---|
| 물건사진1-1 (Eucerin 병, 정면) | bottle ✅ | 0.62 |
| 물건사진1-2 (뚜껑 클로즈업) | bottle ✅ | 0.48 |
| 물건사진1-3 (뚜껑 바닥 각인 코드) | 미탐지 → 원본 폴백 | - |
| 물건사진2-1 (ONE THING 박스 정면) | 미탐지 → 원본 폴백 | - |
| 물건사진2-2 (박스 바닥, 회전됨) | 미탐지 → 원본 폴백 | - |
| 물건사진3 (금색 튜브) | cup으로 오탐 ⚠️ | 0.30 (낮음) |

**6장 중 3장 미탐지, 1장 오탐** — 사전에 문서화했던 한계("통·박스·튜브 형태는 COCO 클래스와 안 맞음")가 정확히 재현됨. 다만 미탐지 시 원본 이미지로 폴백하는 로직이 있어서 파이프라인이 끊기지는 않았다(②에서 확인).

## ② OCR — 크롭(또는 폴백 원본) 6장 + 장바구니 스크린샷 2장

**물건 사진 (인쇄 라벨)**

| 샘플 | 결과 |
|---|---|
| 물건사진1-1 (영문 정면 라벨) | ✅ "Eucerin HYALURON ... ESSENCE" 등 고신뢰도(0.94~1.00)로 정확히 읽힘 |
| 물건사진1-2 (한영 혼용 뒷면) | ⚠️ 부분적으로만 읽힘("하이알루론 부스팅", "expiry date... see packaging") — 실제 유통기한 숫자는 이 면에 없고 "별도 표기"(뚜껑 쪽)라 라벨 위치 자체가 문제 |
| 물건사진1-3 (뚜껑 각인 코드) | ❌ 거의 실패 — "B41457577"을 "E41457577"로 오독, MFG/EXP 숫자 자체는 못 읽음 |
| 물건사진2-1 (박스 정면, YOLO 폴백) | ✅ "ONE THING PEPTIDE RETINAL SERUM" 고신뢰도로 완벽히 읽힘 — **YOLO가 실패해도 원본 폴백으로 OCR은 정상 동작함을 확인** |
| 물건사진2-2 (박스 바닥, 회전됨) | ❌ 거의 완전 실패("g", "동", "틀"만 인식) — 텍스트가 세로/회전돼 있는 게 원인으로 보임(신규 발견 실패 유형) |
| 물건사진3 (금색 튜브 각인) | ⚠️ 마케팅 문구는 부분 인식되나 각인된 유통기한 숫자는 못 읽음(1-3과 동일 유형) |

**장바구니 스크린샷 (디지털 텍스트)**

인쇄 라벨보다 훨씬 정확: "[에스티 로더] 갈색병 세럼 75ml", "[유세린] 하이알루론 부스팅 에센스 100ml" 등 상품명 대부분 정확히 인식. 숫자 0↔9, ㅇ↔ㅁ 등 소소한 오탈자만 있음(예: "249,000원"→"249,009원").

**정리**: 실패 유형이 3가지로 뚜렷이 나뉜다 — (1) 반사광/각인 텍스트(저대비), (2) 회전된 텍스트, (3) 유통기한이 다른 면에 있어서 애초에 프레임에 없는 경우. (1)(2)는 OCR 전처리(대비 보정, 방향 자동 보정)로 개선 여지가 있고, (3)은 사용자 안내(예: "뚜껑/바닥도 찍어주세요")로 보완해야 하는 UX 문제.

## ③ 매칭 + LLM 잔소리 문구 생성

**매칭 로직(difflib)**
| 입력 텍스트 | 결과 | 유사도 |
|---|---|---|
| "에스티 로더 갈색병 세럼 75ml" (장바구니, 한글) | ✅ 매칭됨 → "에스티 로더 갈색병 세럼" | 0.833 |
| "모로칸오일 헤어 트리트먼트 100ml" (장바구니, 있템 목록에 없음) | ✅ 등록 후보로 정확히 분류 | 0.074 |
| "ONE THING PEPTIDE RETINAL SERUM" (영문, 있템 목록에 없음) | ✅ 등록 후보로 정확히 분류 | 0.0 |
| "Eucerin HYALURON..." (물건 사진 OCR, **영문**) vs 있템 목록의 "유세린..."(**한글**) | ❌ 매칭 실패(같은 제품인데 언어가 달라서) | 0.0 |

**신규 발견 한계**: 언어/문자 체계가 다르면(영문 라벨 vs 한글로 저장된 있템 이름) 문자열 유사도 매칭이 아예 통하지 않는다. 실제 서비스에서는 번역/정규화 단계나, 브랜드명 사전 매핑이 필요할 것으로 보임 — PoC의 성공 기준(카테고리/이름 매칭 정확도)에 이 케이스를 실패로 포함해서 계산해야 함.

**LLM 잔소리 문구 생성 (Ollama qwen2.5:3b)**

같은 매칭 결과("에스티 로더 갈색병 세럼")에 대해 3개 프리셋으로 4회 반복 생성:

| 프리셋 | 생성된 문구 (샘플) |
|---|---|
| 다정 | "물론이지 조금 전에 이걸 장바구니에 넣었는데?" |
| 직설 | "이미 가지고 있으니 다시 생각해봐." |
| 매운맛 | "뭐야 너 그거 또 뭐야? 장바구니에서 지우라고!" / "너 이미 가지고 있잖아!" / "이거 또 담으러 가나?" |

톤 차이는 뚜렷하게 느껴짐(다정은 부드러운 되묻는 어투, 직설은 명령형, 매운맛은 감탄사+명령형이 강함). **다만 4회 중 1회는 문구에 한자·영문 잡음이 섞여 나온 적이 있었음**("별 거예요 그냥 안買세요astos") — 재현은 안 됐지만(이후 3회 연속 정상), 로컬 소형 모델(3B)의 간헐적 불안정성으로 기록해둔다. 실제 적용 시 재시도 로직이나 출력 검증(한글/영문만 허용하는 필터)이 필요.

## ④ TTS (macOS `say`)

- 3개 프리셋 모두 음성 파일 생성 성공, 유효한 오디오로 확인(`afinfo`).
- **1차 시도(보이스별 분리) — 버그 발견 및 수정**: 프리셋마다 다른 보이스(다정=Yuna, 직설=Eddy, 매운맛=Grandma)를 썼는데, `Eddy`/`Grandma`처럼 여러 언어에 동명 보이스가 있는 경우 언어 지정 없이 `-v Eddy`만 주면 macOS가 한국어가 아닌 다른 언어 보이스를 골라서 한국어 텍스트가 거의 무음(4800바이트 빈 파일)으로 나오는 문제를 발견함. `"Eddy (한국어(한국))"`처럼 언어까지 정확히 지정해서 해결.
- **2차 시도(속도만 조정)**: 위 수정 후 사용자가 직설/매운맛 속도를 올려달라고 해서 `-r`(rate)만 프리셋별로 다르게 줌(직설 220, 매운맛 240). 그런데 매운맛(`Grandma`)이 여전히 "매끄럽지 않다"는 피드백을 받음 — 원인은 `Eddy`/`Grandma`/`Rocko`/`Sandy` 등 이 시스템의 한국어 보이스 대부분이 macOS 캐릭터(노벨티) 보이스라 합성 품질 자체가 거칠기 때문으로 확인(표준 보이스는 `Yuna`뿐). 이 Mac엔 더 매끄러운 Enhanced/Premium 한국어 보이스가 설치돼 있지 않음.
- **최종(Yuna 하나로 통일 + 속도·피치만 다르게)**: 캐릭터 보이스를 전부 버리고 `Yuna` 표준 보이스 하나로 통일, 대신 `-r`(속도)과 `[[pbas N]]`(피치, 임베디드 스피치 커맨드)을 프리셋별로 다르게 줘서 톤을 구분함. 이 방식이 매끄러움 문제 없이 최종 채택됨. 최종 값(대화 중 사용자 피드백으로 여러 차례 미세 조정):
  - 다정: 기본 속도(~175wpm), 기본 피치
  - 직설: 170wpm(기본보다 살짝 느리게), 피치 -10
  - 매운맛: 235wpm(빠르게), 피치 +15
- **교훈**: macOS `say`는 무료·설치 불필요라 PoC에 편리하지만, 캐릭터 보이스보다 표준 보이스(Yuna)를 톤 파라미터로 변주하는 쪽이 품질이 더 안정적이었다 — 실제 서비스화 시에는 더 자연스러운 상용 TTS(예: 여러 화자를 지원하는 클라우드 TTS)로 교체를 검토할 만함.

## 종합 — 파이프라인 자체 검증

`run_pipeline_demo.py`로 물건사진1-1(Eucerin)을 끝까지 실행: YOLO 크롭 → OCR(영문 라벨 정확히 인식) → 매칭 실패(언어 불일치, 위 한계 참고) → "등록 후보"로 정상 분기, OCR 텍스트가 그대로 등록 폼 프리필용으로 출력됨. 4단계가 에러 없이 끝까지 이어지는 것을 확인했다 — YOLO 미탐지·매칭 실패 같은 "실패"도 파이프라인을 끊지 않고 다음 분기(폴백/등록후보)로 정상 흐르는 것이 이번 실험에서 가장 중요하게 확인된 지점.

## 2차 개선 라운드 결과 (우선순위 1~5 적용)

1차 실험에서 나온 개선 과제를 우선순위대로 실제 적용하고 재검증한 결과.

### ① OCR 회전 보정 — 효과 제한적
`easyocr.readtext()`에 `rotation_info=[90,180,270]` 추가(새 의존성 없음). 회전된 텍스트 실패 사례(물건사진2-2)로 재검증했으나 **개선 안 됨** — 이전엔 "g","동","틀"(잡음 3개)였는데 지금은 "700\*509","z0z","73! 까지"(다른 잡음 3개)로 여전히 실패. 다른 5장은 회귀 없음.
**재분석**: 진짜 원인은 회전이 아니라, YOLO가 이 사진에서 아무것도 탐지 못 해 원본 전체를 그대로 OCR에 넘겼는데 실제 텍스트(바코드+EXP 코드)가 전체 프레임 대비 너무 작아서 EasyOCR이 애초에 그 영역을 텍스트 박스 후보로 잘 못 잡는 것으로 보임. "회전 문제"라고 진단했던 게 실제로는 "텍스트 영역이 너무 작음" 문제였을 가능성 — 원인 진단 자체를 다시 봐야 하는 사례로 기록.

### ② LLM 문구 출력 검증/재시도 — 정상 동작 확인
한글/영문/숫자/기본 문장부호만 허용하는 정규식(`VALID_PHRASE_PATTERN`)으로 이전에 관찰된 잡음("별 거예요 그냥 안買세요astos")을 실제로 걸러내는 것을 확인(`is_valid_phrase()` 유닛 확인: 정상 문구 True, 잡음 문구 False). 3회 재시도 후에도 실패하면 프리셋별 고정 폴백 문구를 반환하도록 함.

### ③ 언어 정규화 매칭 — 부분 개선(입력 노이즈에 민감함을 재확인)
difflib 유사도가 임계값 미만이면 Ollama에게 "같은 제품인지" 의미 기반으로 재판단시키는 `llm_semantic_match()` 추가.

**1차 재검증(성공)**: 비교적 깨끗한 OCR 텍스트("Eucerin HYALURON BoosTING ESSENCE skin hydrates Intensively rovides brightel Pepares 'for routine skincare")로는 `method: "llm"`로 "유세린 하이알루론 부스팅 에센스"와 정확히 매칭됨 — 1차 실험에서 유사도 0으로 완전히 실패했던 케이스가 해결되는 걸 확인. 회귀 확인: 진짜 신규 물건(모로칸오일, ONE THING)은 LLM 폴백을 거쳐도 여전히 "매칭 안 됨"으로 올바르게 분류됨(거짓양성 없음).

**2차 재검증(실패, 정직하게 기록)**: `run_pipeline_demo.py`로 같은 물건사진1-1을 다시 돌렸더니(①에서 `rotation_info`를 추가한 뒤라 OCR 토큰 순서·잡음이 살짝 달라짐) `"...'jayugiiq for skin ... YAiotocicst"`처럼 잡음이 더 섞인 텍스트가 나왔고, 이번엔 `llm_semantic_match`가 3회 모두 "없음"이라고 답해 매칭 실패. **결론: 이 하이브리드 매칭은 "완전히 해결"이 아니라 "부분 개선"이다** — 텍스트가 비교적 깨끗할 때(장바구니의 디지털 텍스트 등)는 잘 작동하지만, OCR 잡음이 많이 섞이면 3B 로컬 모델의 판단도 함께 흔들린다. 더 큰 모델을 쓰거나, LLM에 넘기기 전에 OCR 결과를 정제(잡음 토큰 제거)하는 전처리가 추가로 필요해 보인다.

### ④ 사용기한 미인식 안내 문구 — 초안 작성
아직 실제 등록 UI가 없어 코드가 아니라 `PROBLEM.md`에 문구 후보 3개를 적어둠(예: "사진에서 유통기한을 못 찾았어요. 뚜껑 안쪽이나 포장 바닥도 함께 찍어주시겠어요?"). "다른 면에 있어서 프레임 밖"인 실패 유형에만 효과가 있고, 반사광/각인 실패 유형은 이 안내로 해결 안 됨을 명시.

### ⑤ 카테고리 추천 로직 — 신규 구현, 4/4 정상
`experiments/05_recommend_category.py` 신설. Ollama에게 목업 카테고리 목록(스킨케어/헤어케어/메이크업/바디케어/식품) 중 하나를 고르게 함. 실제 OCR 텍스트 4건으로 테스트:

| 입력 | 추천 카테고리 | 판단 |
|---|---|---|
| Eucerin 에센스 (OCR 텍스트) | 스킨케어 | ✅ |
| ONE THING PEPTIDE RETINAL SERUM | 스킨케어 | ✅ |
| 모로칸오일 헤어 트리트먼트 100ml | 헤어케어 | ✅ |

4건 중 3건 명확히 정확, 1건은 애매한 경계 사례(오답이라기보단 카테고리 체계 자체의 모호함).

## 다음 단계로 넘길 것 (남은 항목)
- 등록 소요시간(수동 vs 자동) 정량 비교 — 실제 등록 폼 통합 시점으로 이월
- 장바구니 레이아웃 다양성 대응 — 특정 쇼핑몰 1~2곳으로 스코프 유지
- ①에서 재분석한 "텍스트 영역이 너무 작을 때"의 진짜 해결책(예: 이미지 업스케일링, 다단계 크롭) 탐색
- 카테고리 체계(스킨케어/바디케어 경계 등) 자체를 다듬을지 여부 검토
